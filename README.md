# iam-legend

> **The GCP IAM toolbelt for AI agents and CI pipelines.** Reads your Terraform, ADK Python, and gcloud scripts, figures out which IAM permissions your *deployer service account* actually needs, checks them against the live project IAM, and posts an AI code review on the PR — before `terraform apply` fails halfway through and leaves your infrastructure half-applied.

Built for the **[Google for Startups AI Agents Challenge 2026](https://googlestartupsaiagents.devpost.com/)**, Track 1 (Build — Net-New Agents).

**Live demo:**
- 🤖 **PR review bot in action:** [iam-legend-validation-demo/pull/1](https://github.com/williamomeara/iam-legend-validation-demo/pull/1) — posted by the bot, on an unmodified Google `agent-starter-pack` project
- 🌐 **Hosted Cloud Run MCP:** `https://iam-legend-935195616837.us-central1.run.app` (read-only, auth-gated)
- 📦 **Action:** `uses: williamomeara/iam-legend@v0.1.1`
- 📐 **Architecture:** [docs/architecture.md](docs/architecture.md)

## What it does

```
parsers/        terraform plan json + .tf static + ADK Python AST + gcloud shell
   ↓
catalog/        2,324 GCP roles + 13,403 perms + 100 curated IaC kinds → required perms
   ↓
gcp/            testIamPermissions against the deployer SA via ADC → live diff
   ↓
recommender/    set-cover proposes 5 candidate bundles → Gemini picks with context
   ↓
reviewer/       Gemini composes PR review prose → posts via PyGithub
```

Three surfaces share one Python core:

1. **MCP server** (FastMCP) — plug into Gemini CLI, Claude Code, Cursor. Ask *"what IAM does this repo need?"* and get a structured answer.
2. **GitHub Action** — runs after `terraform plan`, posts an AI code review on the PR. Blocks deploys with missing permissions before CI fails halfway.
3. **CLI** — `iam-legend review --plan plan.json --project my-proj` for ad-hoc local checks.

**Gemini is off the correctness path.** The math (set-cover, catalog lookups) is deterministic; the LLM provides judgment for role selection + natural prose. Templated fallback fires if Vertex is unreachable — you always get a useful review.

## Quick start — GitHub Action

Add 6 lines to your workflow after `terraform plan`:

```yaml
- uses: google-github-actions/auth@v2
  with:
    workload_identity_provider: ${{ secrets.WIF_PROVIDER }}
    service_account: deployer@my-proj.iam.gserviceaccount.com

- run: terraform plan -out=plan.tfplan && terraform show -json plan.tfplan > plan.json

- uses: williamomeara/iam-legend@v0.1.1
  with:
    terraform-plan: plan.json
    project-id: my-proj
    # Optional: enable real Gemini-written review prose (otherwise templated)
    vertex-project: my-proj
```

The Action runs as the deployer SA (because `google-github-actions/auth` ran first), so `testIamPermissions` answers for the principal that actually runs `terraform apply`.

**No `terraform plan` in your CI?** Drop it — iam-legend's HCL parser reads `.tf` files directly:

```yaml
- uses: williamomeara/iam-legend@v0.1.1
  with:
    working-directory: deployment/terraform
    project-id: my-proj
```

## Quick start — MCP server (local)

```bash
pip install iam-legend  # or: uv pip install iam-legend
```

Then add to your MCP client config (Claude Code, Gemini CLI, Cursor):

```json
{
  "mcpServers": {
    "iam-legend": {
      "command": "iam-legend-mcp"
    }
  }
}
```

The local stdio server runs as your shell user — `gcloud auth application-default login` once and live IAM diff just works. Hosted Cloud Run instances run in **read-only mode** by design; see [Security](#security).

## What's in the catalog (MVP)

- **2,324** predefined GCP roles (full `iam.roles.list` snapshot)
- **13,403** distinct IAM permissions
- **100** curated IaC kinds:
  - ~45 Terraform `google_*` resources (Storage, Compute, Run, GKE, IAM, Pub/Sub, BigQuery, Firestore, Cloud SQL, Secret Manager, Vertex AI Endpoint, **Vertex AI Reasoning Engine**, Discovery Engine, Workload Identity Federation, …)
  - ~25 ADK / Vertex / Gemini Enterprise SDK calls (with import-alias resolution — `from vertexai import agent_engines` is recognised, not just fully-qualified)
  - ~30 gcloud verbs (in shell, Makefile, README code fences)
- **Refresh:** [`catalog_build/refresh_roles.py`](catalog_build/refresh_roles.py) + [`catalog_build/refresh_api_methods.py`](catalog_build/refresh_api_methods.py), runnable weekly via cron

## Hybrid role recommender

Where the v0.1 release decoupled math from explanation (deterministic set-cover picked, Gemini wrote prose about whatever was picked), v0.1.1 does it properly per the design spec §7.4:

1. **set-cover proposes 5 distinct candidates** using 4 different scoring strategies (per-service-prefix, consolidate-broad, narrowest-roles, strict-per-service)
2. **Each candidate carries metadata** (perms covered, extra perms granted, per-service breakdown)
3. **Gemini picks by index** with full context (project, requirement breakdown, candidate metadata, explicit anti-patterns)
4. **The choice is verified** against the catalog (Gemini can't hallucinate non-existent roles)
5. **Deterministic fallback** to candidates[0] if Gemini fails / hallucinates / is unreachable

Result: real reviews on real PRs now read like ([live example](https://github.com/williamomeara/iam-legend-validation-demo/pull/1)):

> *"This PR ✅ looks good for merging once the following IAM roles are granted to the deployer service account. Please add these roles for `iam-legend-demo-deployer@…`: `roles/bigquery.admin`, `roles/iam.devOps` (Note: This role grants broad permissions for `logging.*`, `pubsub.*`, `serviceusage.services.enable`. Please review its specific permissions.), `roles/resourcemanager.projectIamAdmin`. … This PR cannot proceed without these additions, as the deployer is missing essential permissions like `bigquery.tables.create`, `pubsub.topics.create`, and `iam.serviceAccounts.create` required for successful resource provisioning."*

Gemini surfaces concerns in-band (the "broad permissions" note on `roles/iam.devOps`) rather than waiting for a human to notice.

## Security

- **Local stdio MCP:** runs as you. Full toolset including live IAM diff. Uses your existing ADC.
- **Hosted Cloud Run MCP:** runs as a credential-less SA (`roles/aiplatform.user` only, no project IAM read). Static analysis + recommender only. **Does NOT accept user GCP tokens via tool arguments** — that would leak them in transcripts and no MCP client today reliably implements header-based passthrough. Don't trust hosted instances with live diff.
- **GitHub Action:** runs as the deployer SA via Workload Identity Federation. Same ADC mechanism as local stdio. No long-lived service-account keys, no `GOOGLE_APPLICATION_CREDENTIALS` JSON files.

## Honest limitations

- Catalog covers ~100 IaC kinds. Anything outside that surfaces a visible warning on the review (no silent drops).
- Terraform registry modules require `terraform init` for static-mode scanning; CI-mode reads plan JSON which always has them resolved.
- Inline PR comments anchored to lines *outside the diff* are rejected by GitHub's API. iam-legend falls back to top-level-only review automatically — but if your PR modifies few `.tf` lines, most inline annotations land in the workflow log rather than on the PR.
- Gemini calls add ~1-2s of latency to the review (totals ~50s end-to-end with Docker build + Cloud Build cache).
